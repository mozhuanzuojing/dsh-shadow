# ADR-0085: 能力降级台账 —— ADR-0049 的「可见信号」收口到一处

- 状态：**已接受并实现**（2026-09-12 / v1.15.65）
- 关联：**ADR-0049**（缺件不静默：`unavailable` 状态 / flush warn / debug trace **三者至少一个**，
  **`console.log` 不算**）· `BACKLOG.md` **T8 的 A 部分**（7 条静默降级）· `adr/0084`（T8 的 B 部分）·
  `adr/0083` §14.1（路线漂移）· `adr/0003`（派生件不是 source）
- 定位：**纪律**（不是能力）。产出一个机制 + 一条判定「什么算可见信号」的操作口径。

## 1. Context：ADR-0049 早就写下了判据，但**没有承接它的东西**

ADR-0049 的判据很明确（`adr/0049:45` 的自检清单）：任何可选增强「**有可见信号（状态 / warn / debug 之一）**」。
T8（v1.15.34 立账）顺着这条判据查出 **7 处降级没有任何一条信号**，且其中一个形态特别刺眼：

> `core/writer-llm.ts` 的 `streamText` 唯一的痕迹是 `if (opts.label) console.log(...)`。
> 而 `recallSelect` / `knowledgeNavigate` 传的是 `label: ""` ⇒ **连 log 都没有**。
> 更根本的是：`!llm`、`!route`、`finish.reason.kind === "error"|"aborted"` 三条路径
> **从不进 catch** ⇒ **即使有 label 也不会出声**。

⇒ 问题不是「不知道要留痕」，而是**留痕没有承接物**：写侧没有地方可写、读侧没有地方会渲染。
每一处降级各自 `console.log` 的结果，是**七种互不相同的、且大多不可见的**信号。

## 2. 决定一：信号的**唯一承接物**是 `WriterCore.degrade` + `getFlushWarn()`

```
写侧（core/writer-core.ts）      noteDegrade(core, capability, reason, effect)   ← 唯一写入口
                                  ↓
统一渲染（core/writer.ts）        getFlushWarn()  把台账渲染成横幅（每个能力一行）
                                  ↓
所有读路径（query/*.ts）          60+ 处 `+ flushWarn` ⇒ **一处渲染，全部 mode 同时获得信号**
```

**为什么不各能力自己打印**：`getFlushWarn()` 的结果已经被**每一个**读 handler 带在返回值里。
在它里面加一行，所有 mode 同时获得信号，不需要逐个 handler 改。
「判据收一处」在这里的具体含义就是：**「能力降级怎么让读者看见」只有一个答案**。

**为什么读侧也能写**：`queryLog` 与 `recallLedger` 是**读路径**上的降级，它们手里没有 `WriterCore`。
故经 `ShadowQueryDeps.noteDegrade` 注入同一个入口 —— 写侧与读侧写的是**同一个台账**、渲染成**同一个横幅**。

## 3. 决定二：`effect` 是**必填**，且「关掉」不算降级

两条都是为了不让信号退化成噪音：

1. **必须说清后果**（`DegradeNote.effect`）。ADR-0049 要的是「**可见**」，而可见的前提是说清**丢了什么**。
   一句「llmRecall failed」对读者没有用，因为他还得自己推断这会导致什么。
   ⇒ 每条留痕都要回答「你读到的这个东西少了什么 / 可能错在哪」。
2. **用户显式 `enabled: false` 不留痕**。ADR-0049 的判据是「**关掉或**缺件后行为退到某处却无信号」——
   但「关掉」是**用户自己的选择**，把它渲染成告警等于把读者的决定当成故障。
   ⇒ 留痕只在**该工作却没工作**时发生（缺件 / 调用失败 / 后端拒绝 / 坏件）。
   实现上由调用点的条件保证（如 `if (!obsOk && fs && ws && cfg.queryLog?.enabled !== false)`）。

## 4. 决定三：同类**覆盖**，且按能力名排序

- **覆盖**（`Map` 的键是能力名）：一直坏着的能力不该每回合追加一条 ——
  「一直坏着」与「刚刚坏」对读者是同一件事，刷屏只会让信号变成噪音（ADR-0049 的反面）。
- **排序**：`Map` 的插入序会随「哪个先降级」变化 ⇒ 同一状态两次读会得到不同字符串，
  这会让**逐字节比对**的门禁变脆。故渲染前按能力名排序。

## 5. 决定四：`projectionStore` 的静默判为**正当**（T8 第 6 条）

依据是 ADR-0049 **表里的行级豁免**（`adr/0049:38`）：「Projection Store | 缓存文件 |
读失败 / 坏行 → `null` → 重建（**缓存不是真相**，`rm -rf` 无影响）｜可见信号：**否**」。

判为正当的理由是**这条降级不改变答案**：缓存只是性能优化，源（记忆文件）才是真相（ADR-0003），
重建得到的结果与命中缓存**逐字节等价**。对比其他条目 —— 它们的降级会**改变读者看到的内容**
（少摘要 / 窄召回 / 冷却失效 / 观测数据丢失）⇒ 那些必须有信号。

**⚠ 同时记下一处 ADR 内部张力**（诚实标注，本轮不改 ADR）：
同一份 ADR 的「自检清单」（`adr/0049:45`）要求**每一个**可选增强都有可见信号，表里却给了豁免、清单里没写例外。
本轮在 `core/projection-store.ts` 的 `load()` 里就地写明「按表的行级豁免执行」，
免得下一个读者以为清单是绝对的、又来给这里补一条无用的 warn。
**该裁定的失效条件**：若将来这份缓存**参与答案**（存了不可重建的中间判断），它就不再是「缓存不是真相」这一类。

## 6. 落地清单（7 条 → 各自的信号形态）

| # | 能力 | 形态 | 备注 |
|---|---|---|---|
| 1 | `llmRecall` | 台账 + 横幅 | 修掉了「**连 log 都没有**」 |
| 2 | `summary` | 台账 + 横幅 | 「文件里没有摘要」与「尚未生成」此前**不可区分** |
| 3 | `recallExpansion`（语义 B 档） | 台账 + 横幅 | `README` 自称「**静默**退回 A 档」—— 承认写在文档里，读者在输出里看不到 |
| 4 | `queryLog`（**默认开启**） | `recordQueryObservation` 返回 `boolean` → 调用点留痕 | T8 里优先级最高（默认开启项的静默） |
| 5 | `recallLedger` | `readLedger` 区分 `corrupt`/`unreadable` → 调用点留痕 | 修掉「留了 `corrupt` 标记却**没有消费者**」= 等价于没留 |
| 6 | `projectionStore` | **不加信号**（裁定，见 §5） | 缓存不是真相 |
| 7 | `episodes` / 解析 | 台账 + 横幅 | ① 解析失败 ⇒ 该记忆从 Episodes/Decision 里**整个消失**；② 派生失败渲染成「暂无连续任务片段」 |

另：`knowledgeEngine.llmNavigate` 已在 `query/reads.ts:174` **就地披露**「（…LLM 导航未启用/失败 → 确定性检索）」，
本 ADR **不**给它加第二条披露（同一件事只写一处）。它现在多给的是**原因**（`no-route` / `llm-error` …），
与那句「退到了哪里」是两个层级，不重复。

## 7. 我在写测试时犯的两个错（留档，因为它们正是本条的论据）

写 `test/t8-silent-degradation.test.ts` 的**端到端**断言时，我**两次**猜错读路径：

1. 用 `read_shadow({topic})` 去测 `queryLog` —— 实际 `recordQueryObservation` 挂在 `mode:"query"` 上；
2. 用 `mode:"recovery"` 去测 `recallLedger` —— 实际 `readLedger` 在**不传 mode** 的默认召回上，
   而 `recovery` 走的是另一个渲染器（它只是**复用了**前一轮留下的横幅，因为 `flushWarn` 是统一的）。

**两次都是「正对照」把我拦下来的**（第一版的正对照是「健康 fs 下 query-log 必须真的落盘」，
它当场变红，证明代码路径没走到、那句「没有横幅」是**假绿**）。

⇒ 两条教训：
- **端到端断言必须先证明路径真的被走到**，否则「断言通过」只证明「我没测到」。
- **我不该猜读路径**。为此新增取证探针 `.docs/fix/2026-09-12/t8a-read-path-map.ts`，
  把四条路径的**实际输出开头 + 落盘键**打出来，用事实代替猜测。
  这与 `adr/0084` §4 的教训同型（那次是探针自己把判据写窄了）：
  **凡「我以为是那样」的地方，先做一次能证伪的观察。**

## 9. 未做 / 诚实边界

- **`episodeParse` 与 `episodes` 两个生产者只有接线、没有端到端触发**：
  本仓夹具里没有能让 `parseMemory` / `deriveEpisodes` 抛异常的输入 ⇒
  这两条锁的是**机制与接线**（③组同型），不是它们各自的触发路径。**这是缺口，不是已验证。**
- **`recallLedger` 的「写失败」留痕未端到端触发**：`writeLedger` 只在
  `cooldownTurns > 0 && servedDetail.length` 时调用，而 `servedDetail` 需要「tier ≠ L0 且渲染被截断」
  的长记忆 ⇒ 夹具成本较高。本轮锁到「读不到 / 坏件」两种，写失败那条只有接线。
- **`knowledgeNavigate` 的留痕没有专门断言**（与已断言的三个生产者共用同一机制）。
- **一次观察未修**：台账**坏件**时本回合若走到写台账那一步，会把坏件**覆盖**掉
  （内容是 `{}` 派生的 `{turn:1}`）。原文件已无法解析 ⇒ 没有「可用数据」丢失，
  但**手工抢救的机会**同时消失。已在横幅的「后果」里写明；未改成「写到旁路文件」——
  那是另一个决定（需要定「坏件保留多久、谁清理」），不在 T8 范围内。
- `summary` 的降级留痕是**能力级**而非**逐条记忆级**：横幅只说「摘要能力坏了」，
  不说「这 37 条记忆没有摘要」。后者需要逐条记账，成本与噪音都更高。
