## §1 A1：压缩判据 —— **吸收（限面）**，运行时不吸收

### §1.1 先读 `adr/0038` §6 原文（**不转述，直接引**）

`adr/0038` §6 标题即结论：**「方向 A（写侧按 episode 成文件）不做」**（`adr/0038-episode-consolidation-boundary.md:35`）。三条理由**逐字**是：

> ① 实时任务可能长时间 Open（8 小时无收口→无文件）；② **任务边界无法由 agent 自决**（今天"删 Todo+修 U8+调 OpenAPI"是一个还是三个 Episode？）；
> ③ **Agent 无法知道任务何时结束**。

同文件的补记（`:86-91`）把「已经落地的触发点搬迁」与 §6 的关系写死了：
> §6 拒绝的是**写侧按 episode 成文件**，三条理由都是「**任务边界不能由写侧自决**」。本次没有引入任何自决：
> 合并的仍是**已关闭**的 episode（判据是**时间间隔**，客观量）……⇒ 六条边界**一条未松**。

⇒ 所以张力**不是**「模型能不能参与」这种泛化问题，而是**一个可判定的问题**：
**「谁决定 episode / 收口边界」**。材料的 steward 正是**用一次模型调用决定「到点/在途」**（`DeepSeek-Bot@41710f6a` 的
`ds-bot/src/host/steward.js:29-41` 的 `STEWARD_SYSTEM`：`:32` `"switch"`＝到点、`:33` `"compact"`＝在途），
并据此**在运行时换段/收口**（`ds-bot/src/host/parts.js:481-486` 的 `inTurn` / `condense`）。
把它接进本仓的触发条件，就是**让模型判任务边界** ⇒ **直接撞 §6 理由②③**。

### §1.2 张力怎么解（**三条精确边界**）

1. **边界对象**：§6 拒的是「**写侧按自决的任务边界产出/切分文件**」。它**不**禁止「模型产出**候选**、由既有判据处理」——
   本仓已有那一形态：`reflection/` 只产 `candidate`、**不写回**（`adr/0110` 定位）；`adr/0051` 纯函数派生。
2. **运行时唯一决定者**：收口的触发只有**一处** —— 写侧 `core/writer/compact.ts` 的 `maybeCompact`（由 `flush` 调用），
   条件只有两条：`compactCfg.enabled`（开关）与 `gapMinutes`（**客观时间间隔**，`:71` `:74-76`）；
   且**只收口已关闭的 episode**（`:82` 的 `eps.slice(0, -1)`）。**这三处今天没有任何模型句柄**（`maybeCompact(deps, fs, ws)` 三个参数）。
3. **吸收面**：**只吸收「判据」**，判据的**消费方**限定为两类 ——
   **① 人 / 复审者**（设计评审时按 §1.3 自问自答）；**② 将来的「离线」面**（若要落代码，只能落成**产 candidate 的离线 pass**，
   且**必须先另立 ADR**）。**不吸收**的那一半写死在这里：
   > **steward 的运行时二分（模型判定 → 直接决定换段/收口）不吸收**，理由是 `adr/0038` §6 理由②③；
   > 除非先改写 §6（那是另一条 ADR 的事，不在本条）。

⇒ 由此 A1 的结论**不含糊**：**吸收为判据（限面）＋ 运行时不吸收（机制层明确否）**。

### §1.5 按 P1–P5 自检本仓（**两处实测不符 + 一处合规对照**）

**`D1`（真缺陷，实测）：收口产物的用户消息段恒空、`概况` 把用户消息数报成 0。**

- **静态证据（两处口径打架）**：
  · `core/view/episode.ts:200-207`：正文行以 `用户：` 开头 ⇒ 进 **`userMessages`**；其余进 `thinkLines`；
  · `core/writer/render.ts:64`：`atoms.flatMap(a => (a.thinkLines || []).filter(l => /^用户：/.test(l)))` ⇒ **从 `thinkLines` 里找 `用户：`**。
  而 `bodyLines` 只收 `^-\s*\[` 开头的行（`episode.ts:196`），且**要求两个方括号组**才剥前缀（`:198`）⇒
  `thinkLines` 里的行**要么带 `[..] [..]` 前缀、要么带 `- `**，**永远不以 `用户：` 开头** ⇒ 这个过滤器**恒不命中**。
- **实测（可重放，见 §7 ①）**：同一份样例原子，`parseMemory` 得 `userMessages=["原话甲"]`、`thinkLines=[]`；
  经 `deriveEpisodes` + `consolidateText` 得到的收口正文里那一行是
  **`> 概况：0 动作 · 0 用户消息 · 0 决策`**，且 `render.ts:76` 的用户消息列表**一行都没有**。
- **它破的是 P5 的哪一半**：恢复句柄那一半**没问题**（原子保留、`Forget≠Delete`、可回放）；
  破的是「**如实声明**」——收口文件把用户消息**报成 0**（不是漏报而是**错报**），比「有损未声明」更坏。
- **修复面**（本轮**不做**）：`core/writer/render.ts` 取 `userMessages` 而非 `thinkLines`；
  **不动机制**（不改触发条件、不引入模型）。票 `D1`（§6）。

**`V1`（需验证，不直接开票）：解析层把用户消息截到 160 字符且未见声明。**

`core/view/episode.ts:201` 是 `...trim().slice(0, 160)`。它作用在**派生层**（`userMessages` 供 task 触发/约束派生与收口用），
**原文文件**另有上限（见 `N1`）。**判据**：这是**有意的派生层上限**还是随手写的常数？
- 若**有意** ⇒ 必须在代码注释或 `CONTEXT.md` 写明，否则按 `adr/0090`「有损必须声明」**开票**（**开票条件已写明**）；
- 若**随手** ⇒ 与 `D1` 一并修。
本轮**只登记判据**，不判它是缺陷（**未找到任何文档说明这 160 的来源** ⇒ 标**需验证**）。

**`N1`（合规对照，登记）：写入侧对长文本有 600 字符上限，且**截断已自报**。**

`core/retention/collect.ts:27-29`：`CAP = 600`，超限时正文写成 `…（**已截断**：原文 N 字，此处保留前 600 字）` ——
这正是 P5 要的形态（**声明损失量**；「不可复取」由「从未落盘」隐含）。⇒ **合规，不动作**（它解释的正是「为什么本仓的『逐字』是**带上限的逐字**」）。

## §2 A2：写入侧纪律三件 —— 逐条判定

### §2.0 先判**同构性**（不同构就别照搬 —— `adr/0087`）

| 维度 | 材料的一条「记忆条目」（`DeepSeek-Bot@41710f6a`） | 本仓的一条「记忆原子」 |
|---|---|---|
| 谁写的 | **模型/人提炼过的事实**（`ds-bot/src/host/memory.js:337-340` 的 review system prompt） | **一回合的采集结果**（用户话 + 决策 + 动作 + 思维行） |
| 容器 | **一个可改写的文件**，进 **system prompt**（`:97` 语义：两个 `MEMORY.md` 随每次请求走） | **一回合一个文件**，进磁盘目录（不进 prompt） |
| 可写性 | **就地改写**（增/改/删都改同一个文件：`:565` `:596` `:618` 的 `add`/`replace`/`remove`） | **只增不改**：收口只把原子标 `compacted` 移出热集，**文件保留**（`adr/0038` §2 `Compacted ≠ Deleted`） |
| 有界性 | **必须**有界（`MEMORY_LIMITS`：`:35` 的 `entry:300 / main:4_000 / topic:16_000 / topics:40`；超限**硬报错**，`:509` `:517-523` `:551`） | 目录无界；要防的是**热集规模**，已有三件机制：`retention`（forget/hotness）· `compact`（移出活跃集）· 读侧预算（`adr/0088` 的 `renderIndexBudgeted`） |
| 历史 | **靠 journal 补**（`:8` 「every change, with the **line before and after**」） | **靠只增不改 + 归档圈**：`compact.ts:105-108` 在改写`indexes/affaires/<key>.md` **之前**把旧全文写进 `…history/<圈号>.md`（`adr/0110` §2.1「旧圈逐字不动」） |
| 变更可见性 | **给人看**：对话头显示一次「Memory updated」（`:530-539`） | 消费方是 **agent**；读侧输出被**逐字节稳定**约束（见 §2.3） |

⇒ **三件都要按这张表判，而不是按「材料有、本仓没有」判。**

### §2.1 条目硬上限 → **不适用（无消费者）**

材料的 300 字符上限的**消费者**是「**这行要进 prompt**」；本仓没有这条路径：原子**不进任何 prompt 模板**，
单条的长度只影响「谁读它时截断」——而那一层**已有自报截断**（`collect.ts:27-29` 的 600 上限 + 声明；读侧另有 `adr/0090` 的损失行）。
⇒ 加一条「单条原子 ≤ N 字符」的硬上限 = **引入没有消费者的机制**（`adr/0087`），且会与「**只增不改**」（P3 的原文保留诉求）**正面冲突**。
**结论：无缺口（不适用）**，不给票。

### §2.2 变更前后像（journal 式）→ **不适用；派生面已有等价物 ⇒ 也无缺口**

- **对 source（原子）**：它们**从不改写** ⇒ **没有 `before` 可记**。「历史」由「文件保留 + git + 归档圈」承担。
  ⇒ 「journal 前后像」这一件在本仓**没有落点**（**不适用**）。
- **对唯一的就地改写面（派生纪要）**：`appendRing`（`core/writer/compact.ts`）会重写 `> 圈数：N` 那一行，
  **而它改写前先落归档圈**（`compact.ts:105-108`）⇒ **before 像已经有了**（形态不同：整份快照，而非逐行 diff）。**结论：无缺口**。
- ⚠ **别混**：`_meta.json` 的 FS 版本守卫（`adr/0068`）解决的是**并发覆盖**，不是**历史可查** —— 两者判据不同，不得互相顶替。

### §2.3 变更可见性 → **不适用（产品面）；本仓已有一条**更强**的反向判据**

- 材料的「Memory updated」是**给人**在 GUI 里看的（`:530-539` 的 `news`：最近一次变更，**只显示一次**）。本仓的消费者是 **agent**（读 `read_shadow`），
  没有「界面提示」这个面。
- 本仓在**可见性**上有一条**更严**的判据，且**已被断言锁住**：**健康路径的输出逐字节不变** ——
  `core/writer/core.ts` 的 `getFlushWarn` 明确「**只在降级时写**，也只在有记录时才渲染 ⇒ 健康路径输出逐字节不变」，
