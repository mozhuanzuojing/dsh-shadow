## 1. Context：为什么需要它，以及为什么它一直没被做

本仓的**公开面**是「**工具名 + `mode` 串 + 配置键 + 落盘格式**」，而**没有任何兼容性政策**。
**代价已经发生过一次**：ADR-0050（v1.13.0）把旧 `mode` 名**直接废止**，并写明「非『mode 串永远不变』」——
**那次没有任何弃用窗口**，靠的只是 `CHANGELOG` 的可读性。

同时，`adr/0083` §14.1 记下了更重的一条：用户 2026-09-12 定的泳道是 `T8 → T15 → D1/D2/D3 → A段 → …`，
而我在 `T8` 之后连续**五轮**元审查，**T15 一步未动**。**这份 ADR 存在的第一个理由就是终止那件事**：
把「下一阶段的主产物」从一句台账条目变成**已签入的产物**。

## 2. 决定一：契约 ≠ API 清单

采用用户给定的定义（`BACKLOG.md` T15）：一条契约 = **Surface + Semantics + Stability + Allowed Drift + Verification**，
**十条字段缺一不得入册**（`id` / `surface` / `owner` / `semantic meaning` / `stability level` /
`allowed changes` / `forbidden changes` / `evidence` / `verification` / `ratchet`）。

**因此本 ADR 不谎称登记册已完成**：切片 1 交付的是**面清单**（受保护的**面**有哪些）
+ **稳定性分档口径** + **弃用流程**；**逐条的十字段仍未填**（见 §6 未做）。
按用户自己的规则，缺字段的条目**不得入册** —— 故 README 里那一节叫「受保护契约面」，
而**不叫**「已完成登记册」。

## 3. 决定二：稳定性用**内部三档**，且**不自造等级**

D8 已判定：本仓**从不给自己打 `stable`/`beta`/`experimental`**（凭空造等级就是「让文档比事实强」）。
故采用 T15 规格里的**内部语义**三档，判据落在**「违反时的后果」**上，而不是落在「成熟度」上：

| 档 | 判据（一句话） | 违反时的后果 |
|---|---|---|
| **`hard`** | 使用者**已经依赖**它，改了会**让已记录的东西读不出来 / 让调用失败** | 破坏既有记忆或既有调用 ⇒ **必须走弃用流程** |
| **`soft`** | 改了会**改变可观察行为**，但**不破坏数据**（派生件可整份重建 / 提示文本可改） | 需在 `CHANGELOG` 写清；**不需要**弃用窗口 |
| **`experimental`** | **无承诺**；本仓自己都还没有确定的用法 | 可随时改，但**必须在就地可见地标注**（ADR-0049 同族：不许静默） |

**为什么判据是「后果」而不是「成熟度」**：成熟度需要人给组件打分（本仓拒绝做，D8），
而后果是**从代码可核对的**（`core/paths.ts` 里有读路径吗？有生产消费者吗？）。

## 4. 决定三：最小的弃用流程（用户 T15 判据 ②）

**五步，缺一不可**——

1. **旧名至少保留一个版本**（在此期间两种写法都要能用）；
2. **调用旧名返回可见提示**，且提示**必须点名替代品**；**没有替代品就明说「无替代」**，不得留空
   （本仓已有形态：`query/query.ts` 的 `retiredApiMessage`，返回「已废止：X → 请用 Y」）；
3. `CHANGELOG` 写**迁移说明**（怎么改、影响什么）；
4. **移除的时机**：`CHANGELOG` 里要有**跨度 ≥ 1 个版本**的弃用记录（本仓只有一个使用者，
   硬套 major/minor 三段式是形式大于实质 ⇒ 用「弃用记录的存在与跨度」当代替判据）；
5. **未知枚举不得落回默认**：未知 `mode` / 未知 provider / 未知版本一律**显式失败或显式 `unavailable`**，
   **不许静默进默认召回**（`retiredApiMessage` 已有这条；ADR-0049「缺件不静默」同族）。

## 5. 决定四：登记册放 `README.md`，证据指向代码

用户 T15 判据 ③ 明写「把清单放进 `README.md`（而非另开一份易漂移的文档）」⇒ 遵守。
本 ADR 只放**决策与判据**（稳定性分档、弃用流程、为什么这样分），
`README.md` 放**清单本身**（面向使用者），二者分工与本仓 `AGENTS.md` 的「每份文档 owned by 什么」一致。
**每一条都必须带 `文件`（符号名优先）作为 `evidence`** —— 行号会腐烂（v1.15.67 的教训）。

### 3. 因果：`CONTEXT.md` 的「62 个 mode」**是对的**，我上一轮把它判错了（v1.15.71 更正）

## 8.5 第七轮元审查（v1.15.71）：把「62」的因果正过来 —— **受门保护的数不该被没有门的探针推翻**

按 v1.15.70 的教训，**要么现数并写下口径，要么不写数**，不做「批量刷新」。

## 8.6 切片 2（v1.15.72）：十字段填完，以及「**八族里有两族其实没人守**」

> **逐条的 `verification` 不在这里重列**：那是**登记册本体**，在 `README.md` 的表 B 一列里
> （本节只给**结论**）。原因是本仓的纪律「**同一个判据只能有一份实现**」——
> 第一版这里抄了一张 8 行的 `verification` 表，与 `README` 的表 B **逐行重复**（v1.15.73 删）。

**结论（8 条契约按设防强度分三档）**：**6 强 / 1 部分 / 1 无**。
- **强**：`tool-name-v1` · `read-mode-v1` · `retired-mapping-v1` · `memory-file-v1` · `derived-file-v1` · `prompt-segment-v1`
- **部分**：`tool-schema-v1` —— 只守 `mode` 的描述，**参数名无人枚举** ⇒ 删参数不会红
- **无**：`config-keys-v1` —— 顶层 19 键**没有任何枚举门** ⇒ **删键 / 改名没有测试会红**

**这一轮真正学到的东西不是「填了 80 个格子」，而是 `verification` 一列把「谁其实没人守」变成了可读的事实。**

**为什么没有顺手给 `config-keys-v1` 加门 —— 理由只有一个：本轮的范围。**

## 8.8 节序事故（v1.15.73）：我把 `§8.5` 追加到了 `§8.6`/`§8.7` **之后**

**症状**：本节的文件头顺序曾是 `§8 → §8.6 → §8.7 → §8.5`。`§8.5`（第七轮）排在 `§8.6`（第八轮切片）**之后**。
